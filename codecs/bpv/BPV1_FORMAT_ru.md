# BPV1 v4 — активные палитры и PCM-аудио

Версия 2 использует фиксированный профиль:

- блок 4×4;
- **64 общих палитры**;
- 16 цветов в каждой палитре;
- четыре локальных цвета на блок;
- 2 бита на пиксель внутри блока;
- общий банк из 1024 RGB888-цветов хранится один раз на видеопоток.

Декодер продолжает читать BPV1 v1 с 16 палитрами, video-only BPV1 v2 и
BPV1 v3 с PCM-аудио и одним фиксированным банком.

BPV1 v4 использует **активный банк палитр**: каждый ключевой кадр содержит
полный банк, обученный по кадрам соответствующего GOP. Поэтому цвета,
актуальные для новых сцен, добавляются, а переставшие использоваться цвета
автоматически исчезают на границе GOP.

## Организация банка палитр

Рекомендуемый начальный фиксированный банк:

- палитра 0 — 16 уровней серого;
- остальные 63 палитры — 21 оттенок × 3 уровня насыщенности;
- каждая цветная палитра содержит 16 уровней яркости.

В v2/v3 один банк строится по статистике всего ролика. В v4 кодировщик
независимо обучает банк каждого GOP. Смена разрешена только на ключевом кадре,
где одновременно очищаются межкадровые ссылки и словари.

## Независимый блок

Логически полная запись блока содержит:

- 6 бит — номер одной из 64 общих палитр;
- 16 бит — четыре 4-битных индекса цветов внутри выбранной палитры;
- 32 бита — рисунок 16 пикселей по 2 бита.

Итого **54 бита**, или **3,375 бита на пиксель** без учёта режима и служебных полей. Это лишь на 2 бита больше профиля с 16 палитрами.

Текущая эталонная JS/Python-реализация ориентирована на простоту и хранит `paletteIndex` целым байтом. Поэтому `RAW` занимает 9 байт полезной нагрузки. MCU-реализация может упаковать 54 значащих бита в 7 байт.

## Режимы блока

Каждый блок имеет 3-битный режим:

0. `SKIP` — тот же блок на той же позиции предыдущего кадра.
1. `MOTION` — точная копия блока предыдущего кадра со смещением `dx,dy` в блоках.
2. `BLOCK_DICT` — ссылка на ранее встречавшийся полный блок.
3. `PATTERN_DICT` — ссылка только на 2-битный рисунок плюс новая палитра блока и четыре локальных цвета.
4. `RAW` — полная запись блока.

Словари очищаются на ключевых кадрах. Декодер может начать с ключевого кадра и последовательно восстановить GOP без более раннего состояния.

## Контейнер и версии

Magic остаётся `BPV1`.

- версия 1 подразумевает 16×16 цветов;
- версия 2 подразумевает 64×16 цветов и не содержит аудио;
- версия 3 сохраняет видеосинтаксис v2 и добавляет PCM_U8 mono.
- версия 4 сохраняет аудиосинтаксис v3 и переносит банк палитр из заголовка
  файла в каждый ключевой кадр.

Размер банка RGB888:

- v1: 16 × 16 × 3 = 768 байт;
- v2: 64 × 16 × 3 = 3072 байта.
- v3: 64 × 16 × 3 = 3072 байта.
- v4: 3072 байта на ключевой кадр; в заголовке файла банка нет.

В v1/v2 после `search_radius` находится нулевой резервный байт. В v3/v4 этот
байт становится `audio_codec`, после него добавляются:

| Поле | Размер |
| --- | ---: |
| `audio_sample_rate` little-endian | 2 байта |
| `audio_channels` | 1 байт |
| reserved, всегда 0 | 1 байт |

Допустимы `audio_codec=0` с нулевыми аудиополями и
`audio_codec=1` (`PCM_U8`) с одним каналом. Рабочий профиль плееров —
unsigned 8-bit mono, 16 кГц.

Заголовок кадра v1/v2 занимает 9 байт:
`keyframe:u8`, `frame_bytes:u32`, `mode_bytes:u32`. В v3/v4 после него
добавлено `audio_bytes:u32`, поэтому заголовок занимает 13 байт.

Полезная нагрузка обычного кадра:
`mode_map[mode_bytes]`, данные блоков, затем `audio[audio_bytes]`.
В ключевом кадре v4 перед картой режимов добавляется
`active_palette[3072]`. Значение `frame_bytes` включает активную палитру,
карту режимов и данные блоков, но не аудио.

Каждый ключевой кадр v4 содержит полный банк, поэтому с него можно начать
декодирование без состояния более раннего GOP. Повреждение одного обновления
палитры также не распространяется дальше следующего ключевого кадра.

## Оценка RAM для 320×200

Кадр содержит 80×50 = 4000 блоков.

При словарях по 256 элементов и 7-байтовом упакованном состоянии блока:

| Компонент | RAM |
| --- | ---: |
| Предыдущий кадр, 4000×7 | 28 000 байт |
| Три строки блоков для `MOTION ±2` | 1 680 байт |
| Словарь полных блоков, 256×7 | 1 792 байта |
| Словарь рисунков, 256×4 | 1 024 байта |
| 3-битные режимы 4000 блоков | 1 500 байт |
| 64×16 цветов RGB888 | 3 072 байта |
| **Основные структуры** | **37 068 байт** |

С небольшим входным буфером, стеком и служебными переменными практический бюджет составляет примерно **39–42 КиБ RAM**, без полноэкранного framebuffer.

В простой реализации с 9 байтами на состояние блока потребуется примерно **47–50 КиБ**. Полный framebuffer RGB565 добавляет ещё 128 000 байт, поэтому для микроконтроллера предпочтителен вывод блоками или несколькими строками прямо в LCD.

## Следующие улучшения

- разрежённые обновления только изменившихся палитр;
- упаковка `RAW` в 54 бита;
- RLE для последовательностей `SKIP`;
- более короткие коды частых режимов;
- дельта локальной палитры относительно предыдущего блока;
- ограниченные словари 256/512 элементов для MCU;
- RGB565 или смешанный RGB565/RGB888 банк;
- индекс ключевых кадров для быстрого перехода.
